## The epic in one paragraph

Net/component connectivity becomes **server-owned derived data** (`Connectivity`, Phase 2). Both C# clients privately re-implement the netlist→component join and key per-component nets by `(side, ComponentRecord.Id)`; the server never populates `Id`, so on a real design all components on a side collapse into one net bucket. The plan deletes the client joins, populates the ODB++ `id` server-side as a typed field (Phase 1), and ships a server-derived `Connectivity` message that clients consume instead of joining (Phase 2), with a golden-file conformance harness (M0.3/M3.3) making any re-introduced join fail a test.

## Standing risk

**Per-environment deploy constraint:** no server build with populated `id` may reach an environment whose clients still resolve `componentNumber` by `Id` (~10% silent mis-resolution on Panel-shaped designs). It is a deploy constraint, not a merge-order one — and F1's landing in both clients front-runs it entirely. Also worth keeping in view: the `dev/*` → `development` shortcut that made `nam20485` a stale base once already (implementation plan §Branch base) — sync from `nam20485` before opening each PR.
